# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

scadustats extracts statistics from Elden Ring "Bingo Brawlers" match videos.

## Setup and commands

- `ffmpeg` must be installed on the system (e.g. `brew install ffmpeg`) — yt-dlp needs it to merge downloaded video/audio streams; without it, downloads fail with `DownloadError: ... ffmpeg is not installed`.
- `tesseract` must be installed on the system (e.g. `brew install tesseract`) — `pytesseract` shells out to it for OCR (goal text, player names, the game label, and the timer) during extraction.
- Dependency management and running: `uv` (not pip/venv directly).
- Install/sync environment: `uv sync`
- Run a script in the project environment: `uv run python -c "..."` or `uv run <entry point>`
- Build distributable (wheel/sdist): `uv build` (backed by hatchling)

## Architecture

- Build backend: `hatchling`, configured in `pyproject.toml`.
- Package layout is flat (no `src/` directory) — the importable package `scadustats` lives at the repo root, alongside `pyproject.toml`.
- `pyproject.toml` explicitly declares `[tool.hatch.build.targets.wheel] packages = ["scadustats"]` since the flat layout requires hatchling to be told which directory is the package.

### Downloading videos (`scadustats/download.py`)

- `download_video` shells out to the `yt-dlp` CLI binary via `subprocess.run` rather than driving the `yt_dlp` Python API. This keeps the invocation a direct, readable equivalent of the documented CLI command (`yt-dlp -f "bestvideo[height<=720]" <URL>`).
- Format is fixed to `bestvideo[height<=720]` — video-only, no audio track, capped at 720p — since this project only needs footage for stats extraction, not playback.
- The final path is recovered from `--print after_move:filepath`, which yt-dlp resolves after its internal move-to-destination step, rather than reconstructing the filename manually (extensions can vary by source format).

### Extracting stats (`scadustats/extract.py` and friends)

The Bingo Brawlers broadcast overlay (5x5 goal grid with per-cell claim color, a score bar per player, a stopwatch timer, a "GAME N" label) is a fixed template that scales proportionally with output resolution — confirmed by comparing a 1280x720 and a 1920x1080 recording of the same template. This shapes most of the design below:

- `layout.py` stores every overlay region (grid, timer, label, score bars) as **fractional** bounding boxes (0-1 of frame width/height), not pixels, so one calibrated config works across resolutions instead of needing per-resolution constants. Recalibrate with `scripts/calibrate_layout.py <video_path>` (draws the configured boxes on a frame for visual verification) if a future season changes the template.
- A single video isn't *only* live gameplay footage: it also contains **"POST GAME" recap segments** that reuse the exact same grid/score-bar coordinates to cycle through a slideshow of other completed games' final boards, but replace the colored score bars with plain background and move the timer elsewhere. `board.is_gameplay_frame` gates every sample on the score bars actually being red/blue before doing any cell/timer/label reading — during a recap this reliably reads as plain background on *both* sides, unlike any real gameplay state. Frames that fail this check are skipped entirely in `extract.py`, rather than trying to interpret whatever the recap happens to be showing at the sampled coordinates.
- `board.py` classifies each cell's claim color by **raw BGR channel dominance** (`red - blue`, `blue - red`, with a `red - green` contrast check to reject an unrelated "orange flash" artifact), not HSV hue. Hue was tried first and looked solid on a handful of calibration frames (red ≈177°, blue ≈104°), but a full ~4-hour-video scan showed a genuinely, continuously red cell drifting from hue 177 down to 152 within seconds of real compressed footage while saturation stayed high — any hue band tight enough to reject a progress-badge contamination artifact was also tight enough to intermittently drop that genuine reading, causing claim-detection flicker. Raw R-vs-B dominance stayed rock-stable (~90-98 margin) across that same drift window. A pure RGB-distance-to-centroid approach was tried even earlier and was separately fooled by a whole-frame brightness swing (a stream fade-in/flash before the overlay appears); dominance-plus-contrast rejects that case too. If reclassification issues resurface, re-derive thresholds empirically from a full-video scan (sample every few seconds, dump per-cell BGR/HSV, look at real distributions) rather than calibrating from a couple of frames again — a handful of frames looked deceptively clean here.
- Color is sampled from a small patch inset at each cell's **corner**, not its center, specifically to dodge the centered goal text and a numeric progress-count badge that appears near the center/corner for multi-count goals.
- A cell can be **unmarked after being marked**: a player can inadvertently claim the wrong square and undo it. `extract.py`'s claim detection therefore treats `UNCLAIMED -> RED/BLUE` as a claim and `RED/BLUE -> UNCLAIMED` as an equally legitimate unclaim (`ClaimEvent.event_type`), not as a data-quality anomaly. Only a *direct* `RED <-> BLUE` swap with no intervening unclaim is still logged as a warning, since real game rules don't seem to support a square directly changing hands. A color change is only accepted once the same new color has been observed on **two consecutive samples** — this debounce is what stops transient single-frame classification flicker (e.g. a stream wipe/flash whose color transiently matches a reference) from being recorded as a real claim or unclaim.
- Winner determination (`extract._determine_winner`) replays *all* events, including unclaims, to the **final** board state and evaluates the win condition once there, rather than stopping at the first claim that completes a line — a mistaken claim can complete a line and be immediately unclaimed, and the schema doesn't record a win timestamp anyway, so nothing is lost by only checking the end state.
- `segmentation.py` requires **at least 2 of 3 independent signals** to agree before declaring a new game boundary, since a single video can contain multiple back-to-back games and each signal alone is individually noisy: (1) the board resetting to fully unclaimed; (2) the timer jumping *backward by a large amount* (not just "any decrease" — a game apparently has its own multi-minute pre-game countdown that legitimately ticks down by ~1/sample, which would otherwise look like a reset on every single sample); (3) the "GAME N" label text changing, where a new label is only trusted once read *identically twice in a row* (OCR noise on this field is severe in practice — a stable "GAME 2" was read as a different garbled string on nearly every sample, so naively comparing every read against the last would fire constantly; noise essentially never repeats itself exactly, so requiring one repeat is a cheap, effective floor). The label is also only OCR'd on a fraction of samples (comparatively expensive), so its change-detection compares against the most recently *seen* non-`None` label, not the strictly-adjacent observation, which would almost always be `None`.
- The live claim count from `board.py` is cross-checked against the OCR'd scoreboard numbers on every count change, logging a warning on mismatch — free validation since the broadcast already renders that number.
- Re-running `extract` on an already-extracted video defaults to `--if-exists replace` (overwrite that video's prior rows) rather than accumulating duplicates, since iterating on calibration/bugfixes and re-extracting is the expected common workflow.
- `json_export.py` optionally writes one flat, pretty-printed JSON file per game (`<json_dir>/<video_id>-<game_index>.json`, opt-in via `extract --json-dir`) alongside the DuckDB write, using the same `<video_id>-<game_index>` id as the DB's `game_id` (db.py:102) so the two stay cross-referenceable — this exists purely so a contributor can hand-review/correct one game's extraction results in a plain text editor without touching DuckDB directly; there's no importer back from JSON into the DB yet, that's a deliberate follow-up, not an oversight.
- The CLI shows a progress bar (`typer.progressbar`) for `extract`, since a full video can take minutes to process at ~1 sample/second. `extract._collect_observations` accepts an `on_progress` callback fired once per sampled frame (including frames later skipped as non-gameplay, since decode cost is paid either way), and `extract.estimate_sample_count` gives the CLI an upfront total (`ceil(duration_s * sample_rate_hz)`, an estimate — exact count depends on where decoding stops near the end) to size the bar before extraction starts.
- `frames.sample_frames` decodes sequentially with `cap.grab()`/`cap.retrieve()` rather than seeking to each target timestamp with `CAP_PROP_POS_MSEC` — profiling showed the seek-per-sample pattern cost ~2.5x more than sequential grab+skip on a real clip, since `CAP_PROP_POS_MSEC` forces a jump back to the nearest preceding keyframe and a forward decode to the target on *every single sample*. This was a genuinely free win (same yielded timestamps/frames, no behavior change) — but it's a minority of extraction's total runtime: profiling the full pipeline on the committed fixture showed OCR (`pytesseract`, which shells out per call) at ~80-90% of wall time, with the per-sample `timer.read_timer` OCR call alone responsible for roughly half of it, since — unlike the game-label OCR — it isn't throttled.
- OCR calls that don't depend on each other run concurrently via a `ThreadPoolExecutor`, since each `pytesseract` call blocks on an external `tesseract` subprocess and releases the GIL while waiting — this took the fixture clip's end-to-end extraction time from ~11.4s to ~2.8s (measured with `cProfile`/wall-clock timing, not just an estimate). Two call sites: `extract._collect_observations` submits each sample's timer (and, every `_LABEL_SAMPLE_INTERVAL`th sample, label) OCR to a shared pool bounded by `_OCR_WORKERS` (`min(8, os.cpu_count())`), gated by a `threading.Semaphore` acquired before every `submit()` — without that bound, decoding (now fast, see above) would race far ahead of OCR and queue the entire video's frames in memory before any of them finished processing; results are still collected in original sample order afterward, so downstream ordering (segmentation, event diffing) is unaffected. `board.cell_square_texts` parallelizes its 25 independent per-cell reads the same way, but as one unbounded one-shot batch (`max_workers=len(crops)`) since it only runs once per detected game, not once per video sample. Neither call site changes *what* gets OCR'd or how often — only wall-clock time — so there's no accuracy tradeoff here, unlike throttling the timer read would be.
- `tests/fixtures/clip_claim.mp4` is a short (80s), re-encoded, full-resolution clip trimmed from a real match, covering exactly one known claim transition — downscaling it for size once broke goal-text OCR (crops became too small to read reliably), so it's kept at source resolution instead and just trimmed/re-encoded to stay small.
- All three committed fixtures (`hud_start.png`, `hud_partial.png`, `clip_claim.mp4`) have the webcam/face regions blacked out (players' and commentators' likenesses aren't needed for testing the overlay-reading logic) — done by zeroing everything outside the grid column and score-bar strip except the timer and game-label boxes, which sit inside those columns and are still needed. Regenerate via the same crop math in `layout.py` (grid/score-bar boxes define the columns to redact; timer/label boxes are restored on top) if new fixtures are ever captured, rather than committing raw frames.

## Testing

- Test runner: `pytest` (dev dependency, declared under `[dependency-groups] dev` in `pyproject.toml`).
- Tests that hit real external services (currently: downloading an actual YouTube video) are marked `@pytest.mark.integration`.
- `[tool.pytest.ini_options] addopts = "-m 'not integration'"` excludes integration tests by default, so a plain `uv run pytest` (or local dev loop) stays fast and offline.
- Run integration tests explicitly with `uv run pytest -m integration`.

## CI

- GitHub Actions workflow at `.github/workflows/ci.yml`, triggered on push to `main` and on pull requests.
- Steps: install `ffmpeg`, install `uv` (`astral-sh/setup-uv`), `uv sync --locked`, `uv build`, then `uv run pytest` (unit tests, default marker filter applies).
- The integration suite (`uv run pytest -m integration`) is *not* run in CI: it hits real YouTube via `yt-dlp` to download a video, and GitHub Actions runner IPs get throttled/bot-detected by YouTube badly enough to cause CI timeouts. Run it locally instead (see Testing section).
