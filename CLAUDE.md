# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

scadustats extracts statistics from Elden Ring "Bingo Brawlers" match videos.

## Setup and commands

- `ffmpeg` must be installed on the system (e.g. `brew install ffmpeg`) — yt-dlp needs it to merge downloaded video/audio streams; without it, downloads fail with `DownloadError: ... ffmpeg is not installed`.
- `tesseract` must be installed on the system (e.g. `brew install tesseract`) — `pytesseract` shells out to it for OCR (goal text, player names, the BASE GAME/DLC label, and the timer) during extraction.
- Dependency management and running: `uv` (not pip/venv directly).
- Install/sync environment: `uv sync`
- Run a script in the project environment: `uv run python -c "..."` or `uv run <entry point>`
- Build distributable (wheel/sdist): `uv build` (backed by hatchling)

## Architecture

- Build backend: `hatchling`, configured in `pyproject.toml`.
- Package layout is flat (no `src/` directory) — the importable package `scadustats` lives at the repo root, alongside `pyproject.toml`.
- `pyproject.toml` explicitly declares `[tool.hatch.build.targets.wheel] packages = ["scadustats"]` since the flat layout requires hatchling to be told which directory is the package. Subpackages come along automatically; nothing needs listing per namespace.
- The package's modules are grouped into six namespaces, with `models.py` left at the root because every namespace imports it and nesting the shared vocabulary under any one of them would be arbitrary:

  | namespace | modules | what it is |
  | --- | --- | --- |
  | `video/` | `download`, `frames` | acquiring footage (yt-dlp) and decoding it into frames |
  | `overlay/` | `layout`, `ocr`, `board`, `timer`, `scoreboard`, `commentators`, `game_type_label` | turning one frame into a reading; the only modules that touch `cv2`/`pytesseract` |
  | `rules/` | `winner`, `validation` | board replay, win conditions, tournament-rule checks — pure Python, no frames or I/O |
  | `pipeline/` | `extract`, `segmentation`, `squares` (+ `squares.json`) | assembling readings into a `VideoExtraction` |
  | `storage/` | `json_export`, `db` | persistence (the JSON file is the source of truth, see below) |
  | `cli/` | `app` (the Typer entry point, `scadustats.cli.app:main`), `display` | flags, prompts, and the rendering they print |

  Imports run strictly one way — `cli` → `pipeline` → {`overlay`, `video`, `rules`, `storage`} → `models` — with one deliberate exception: `pipeline/extract.py` imports `storage/json_export.py`, because writing the JSON is part of `extract_video`'s contract (see below). Every `__init__.py` is a docstring only: nothing is re-exported, so a call site always names the namespace it's reaching into (`from scadustats.overlay import board, ocr`) and there's no import cycle to trip over. `tests/` mirrors the same six directories, and `overlay/game_type_label.py` keeps its `_label` suffix (rather than shortening to `game_type` alongside its siblings) because `extract.py` binds a local `game_type` at the very call site that uses the module — the shorter name would be shadowed exactly where it's needed.

### Downloading videos (`scadustats/video/download.py`)

- `download_video` shells out to the `yt-dlp` CLI binary via `subprocess.run` rather than driving the `yt_dlp` Python API. This keeps the invocation a direct, readable equivalent of the documented CLI command (`yt-dlp -f "bestvideo[height<=720]" <URL>`).
- Format is fixed to `bestvideo[height<=720]` — video-only, no audio track, capped at 720p — since this project only needs footage for stats extraction, not playback.
- The final path is recovered from `--print after_move:filepath`, which yt-dlp resolves after its internal move-to-destination step, rather than reconstructing the filename manually (extensions can vary by source format).

### Extracting stats (`scadustats/pipeline/extract.py` and friends)

The Bingo Brawlers broadcast overlay (5x5 goal grid with per-cell claim color, a score bar per player, a stopwatch timer, a "GAME N" label) is a fixed template that scales proportionally with output resolution — confirmed by comparing a 1280x720 and a 1920x1080 recording of the same template. This shapes most of the design below:

- `layout.py` stores every overlay region (grid, timer, game-type subtitle, score bars) as **fractional** bounding boxes (0-1 of frame width/height), not pixels, so one calibrated config works across resolutions instead of needing per-resolution constants. Recalibrate with `scripts/calibrate_layout.py <video_path>` (draws the configured boxes on a frame for visual verification) if a future season changes the template.
- A single video isn't *only* live gameplay footage: it also contains **"POST GAME" recap segments** that reuse the exact same grid/score-bar coordinates to cycle through a slideshow of other completed games' final boards, but replace the colored score bars with plain background and move the timer elsewhere. `board.is_gameplay_frame` gates every sample on the score bars actually being red/blue before doing any cell or timer reading — during a recap this reliably reads as plain background on *both* sides, unlike any real gameplay state. Frames that fail this check are skipped entirely in `extract.py`, rather than trying to interpret whatever the recap happens to be showing at the sampled coordinates. There's a second non-gameplay state that check can't see, though: the **splash between two games**, where the score bars stay colored but the grid and the timer are both torn down for a handful of samples. An unreadable timer is the tell, so `extract._collect_observations` drops any sample whose timer OCR came back `None` — later than `is_gameplay_frame` does, necessarily, since it needs the OCR result in hand. Reading cell colors off that splash used to produce a burst of spurious unmarks that wiped the just-finished game's winning line out of its final board state, costing game 1 of a real two-game video its winner. Genuinely unreadable timers are otherwise vanishingly rare (8 of 6280 gameplay samples on that video — all 8 of them this exact transition), so this drops essentially nothing else; if more than `_UNREADABLE_TIMER_WARN_FRACTION` (5%) of samples go this way it's a sign the timer isn't being read at all (a miscalibrated `TIMER_BOX`, too low-bitrate a source) and a warning is logged, since the failure would otherwise look like a quiet, successful extraction of a near-empty game.
- `board.py` classifies each cell's claim color by **raw BGR channel dominance** (`red - blue`, `blue - red`, with a `red - green` contrast check to reject an unrelated "orange flash" artifact), not HSV hue. Hue was tried first and looked solid on a handful of calibration frames (red ≈177°, blue ≈104°), but a full ~4-hour-video scan showed a genuinely, continuously red cell drifting from hue 177 down to 152 within seconds of real compressed footage while saturation stayed high — any hue band tight enough to reject a progress-badge contamination artifact was also tight enough to intermittently drop that genuine reading, causing claim-detection flicker. Raw R-vs-B dominance stayed rock-stable (~90-98 margin) across that same drift window. A pure RGB-distance-to-centroid approach was tried even earlier and was separately fooled by a whole-frame brightness swing (a stream fade-in/flash before the overlay appears); dominance-plus-contrast rejects that case too. If reclassification issues resurface, re-derive thresholds empirically from a full-video scan (sample every few seconds, dump per-cell BGR/HSV, look at real distributions) rather than calibrating from a couple of frames again — a handful of frames looked deceptively clean here.
- Color is sampled from a small patch inset at each cell's **corner**, not its center, specifically to dodge the centered goal text and a numeric progress-count badge that appears near the center/corner for multi-count goals.
- A cell can be **unmarked after being marked**: a player can inadvertently claim the wrong square and undo it. `extract.py`'s claim detection therefore treats `UNCLAIMED -> RED/BLUE` as a claim and `RED/BLUE -> UNCLAIMED` as an equally legitimate unclaim (`GameEvent.event_type`), not as a data-quality anomaly. Only a *direct* `RED <-> BLUE` swap with no intervening unclaim is still logged as a warning, since real game rules don't seem to support a square directly changing hands. A color change is only accepted once the same new color has been observed on **two consecutive samples** — this debounce is what stops transient single-frame classification flicker (e.g. a stream wipe/flash whose color transiently matches a reference) from being recorded as a real claim or unclaim. Unclaiming needs more than that, though: `_UNMARK_DEBOUNCE_SAMPLES` requires **twice** the baseline run (4 consecutive samples) to confirm a `RED/BLUE -> UNCLAIMED` transition, while a claim (or the anomalous direct swap) still only needs the baseline `_MARK_DEBOUNCE_SAMPLES` (2). Unclaiming is the direction real flicker falls into by default — a dulled or compression-damaged color patch reads as `UNCLAIMED` far more readily than a stray couple of frames invent a false `RED`/`BLUE` out of nothing (this is exactly the failure mode the splash-transition regression below produced) — and it's also the rarer, more consequential direction: a genuine unclaim is a deliberate undo that then persists for the rest of the game, so demanding a longer run costs real detections next to nothing while meaningfully cutting the false positives a couple of misread frames used to produce.
- Not every event is about a square. `EventType.GAME_START` marks the moment the overlay's stopwatch stops being a **pre-game countdown** and becomes the actual ascending game clock: `extract._detect_game_start` scans a segment's timer readings for the first strict local minimum (previous reading higher, next reading higher again) and emits a `GameEvent` there with `row`/`col`/`color` all `None`. A minimum only counts if the reading *continues* out of it by at most `_CLOCK_STEP_TOLERANCE_S` (30s, generous slack over the ~1s/sample a running clock shows): a segment after the first can open on the tail of the previous screen's short countdown, observed on a real match as `...3, 2, 1` and then straight to `180` — the game's own 3-minute countdown, which only then descends to 0 and ascends as the game clock. That `1` is a genuine strict local minimum, so without the continuity check game 2's start was reported ~3 minutes early, at the wrong dip. `GameEvent` (models.py; the `models.ClaimEvent`/`GameResult.claims`/DB `claims` table/`claim_id` names from earlier in the project's history were renamed to `GameEvent`/`GameResult.events`/`events`/`event_id` once a non-square event type existed) carries `row`/`col`/`color` as optional specifically so a game-level event can omit them; `db.py`'s `events` table and `json_export.py`'s per-event dict serialize them as SQL `NULL`/JSON `null` in that case. Returns `None` (no event emitted) if the segment never shows a descend-then-ascend dip — e.g. footage that starts mid-game with no countdown captured.
- `commentators.py` reads the two commentators' names off the nameplates the overlay prints under the two *inner* webcams (`layout.COMMENTATOR_BOX_LEFT`/`RIGHT`) — the outer pair are the players' own cams and carry no nameplate (their names are read from the score strip instead, see `scoreboard.py`). Symmetric geometry (x 220-450/830-1060, y 671-706 on a 720p frame) confirmed against two independent real matches. A blank crop — every pre-existing fixture, since the nameplate boxes weren't in the redacted set until this was added — isn't simply unreadable: Tesseract hallucinates a plausible-looking token (`"re"`) off a uniform black image, which would otherwise be recorded as somebody's name. `commentators._has_nameplate` gates on the share of near-white pixels in the crop (a plate is bright text on a dark bar; real plates measured 8-10% versus exactly 0% for a blank region) before OCR runs at all — the same "check the precondition, skip entirely if it fails" shape as `board.is_gameplay_frame`. The name itself is recovered as the longest run of `[A-Za-z0-9_.-]` in the reading (`commentators._clean_name`) rather than reusing `scoreboard._clean_name`'s letters-only rule, which would cut a handle like `star0chris` down to `chris` — a streaming handle can contain digits and underscores that a player's display name doesn't need to. `extract_video` reads this once per video (not once per game, same reasoning as player names) off the frames already grabbed for square-text majority voting, majority-voted the same way (`commentators.majority_commentator_names`) since a single frame can misread and a nameplate is static for the whole broadcast. The result is a flat, ordered `list[str]` (`VideoExtraction.commentators`), not two named seats: which webcam a commentator happened to sit in isn't a property of the match, and a plate that never reads is dropped rather than left as a gap or a `None`. `db.py`'s `commentators` table (`video_id`, `position`, `name`) mirrors that shape — one row per name, ordered by `position` — rather than a fixed-width pair of columns, since nothing about the overlay guarantees exactly two commentators going forward. It's a brand-new table, so it needs no `ALTER TABLE ... ADD COLUMN` fixup the way `duration_s`/`win_line` did: `CREATE TABLE IF NOT EXISTS` already handles a database file that predates it.
- Winner determination (`extract._determine_winner`) replays *all* events, including unclaims, to the **final** board state and evaluates the win condition once there, rather than stopping at the first claim that completes a line — a mistaken claim can complete a line and be immediately unclaimed, and the schema doesn't record a win timestamp anyway, so nothing is lost by only checking the end state.
- A LINE win also records **which** line it was won on, as `GameResult.win_line` (`models.WinLine`: `row_1`-`row_5`, `col_1`-`col_5`, `diagonal_tl_br`, `diagonal_bl_tr`; `None` for every non-line outcome, since there's no line to name). Row/column indices are **1-based**, matching `GameEvent.row`/`col` and the `squares` table — a JSON file shows `"win_line": "row_1"` a few lines from a claim's `"row": 1`, so a contributor hand-reviewing the file sees one consistent numbering throughout rather than the board's visual first row being labeled `0`. Internal board/list indexing (`winner.Board`, `overlay/layout.py`'s pixel math, `overlay/board.py`'s cell iteration) stays plain 0-based Python list indices regardless — the offset is applied only at the points where a 0-based loop index becomes a stored `GameEvent.row`/`col`, DB `row`/`col` column, or `WinLine` value (`extract._extract_events`, `db.write_extraction`'s `squares` insert, `winner.LINES`), and reversed wherever a 1-based value is used to index back into a 0-based list (`winner.apply_event`, `json_export._event_square_text`, `display._square_text`). `winner.LINES` is therefore a `dict[WinLine, list[Coord]]` built from the indices rather than written out twelve times (that's what keeps each key's coordinates guaranteed to match the name it's filed under, `Coord` itself staying a 0-based board index even though the `WinLine` key built alongside it is 1-based), and `winner.winning_line` — the old `check_line_winner`, renamed now that it returns more than a color — returns the color and the line *together* so a caller can't attribute a line to the wrong player. `determine_winner` returns a `(color, win_type, win_line)` triple. `WinLine.label` renders the value as prose ("row 1", "diagonal (top-left to bottom-right)") for `match show` and validation messages; the stored value stays the machine-readable one.
- `segmentation.py` requires **both of its two independent signals** to agree before declaring a new game boundary, since a single video can contain multiple back-to-back games and each signal alone is individually noisy: (1) the board resetting to fully unclaimed; (2) the timer jumping *backward by a large amount* (not just "any decrease" — a game apparently has its own multi-minute pre-game countdown that legitimately ticks down by ~1/sample, which would otherwise look like a reset on every single sample), compared against the most recently *seen* reading rather than the strictly-adjacent one, since the timer is unreadable (`None`) for a handful of samples during exactly the overlay transition a reset happens in — observed on a real match as a frozen 3123s final reading, ~8 unreadable samples, then a fresh countdown at 7s, a drop an adjacent-pair comparison never sees at all. There used to be a third signal, the "GAME N" label text changing, and the rule used to be "at least 2 of 3". It was removed because it never earned its keep: on a real two-game video it produced 18 "confirmed" changes, 17 of them OCR noise (`GARE Zz`, `GANIC Zz`, … for a board reading "GAME 2"), and the one genuine change was only confirmed 15 samples after the fact — well outside the agreement window — so it contributed nothing to detecting the real boundary it was watching for, while costing one throttled `tesseract` call every 5 samples. `detect_boundaries` returns **positions within the observation list**, not `Observation.sample_index` values — the two only coincide when every sampled frame was a gameplay frame, and they diverge in practice because non-gameplay frames (the "POST GAME" recap *between* games) never become observations. Returning sample indices made `extract._segment_games` slice the list at the wrong offsets — past its end, in the video that surfaced this — so every game after the first was silently dropped and one segment spanned the whole video. The agreement/collapse windows are still measured in `sample_index`, so "within 5 samples" means 5 sampled frames of real footage rather than 5 surviving observations with an arbitrary stretch of skipped recap in between.
- The live claim count from `board.py` is cross-checked against the OCR'd scoreboard numbers on every count change, logging a warning on mismatch — free validation since the broadcast already renders that number.
- `video_id` (`extract._video_id`) is `<match-date>-<red player>-vs-<blue-player>` (e.g. `2026-03-05-blanxz-vs-Serious`), not the video file's name — a file's name is often a descriptive title (see the pre-existing files under `matches/`), not a stable/parseable identifier, whereas this format is both human-readable and sorts/groups sensibly. It's built from `match_metadata`'s match date plus the first detected game's OCR'd player names. `match_metadata` is therefore a required argument to `extract_video`, not optional — video_id can't be formed without it. Missing/empty player names (`scoreboard.read_player_names` can return `""` on a bad OCR read, or there's no game at all) fall back to `"unknown"`; a `/` in a name is replaced with `-` since it would otherwise split into a spurious path segment when the id is used as a filename. Season and match type are still collected and stored (in the JSON body and, via `load-db`, the DB) — they're just not part of the id.
- One JSON file represents one *video* (`models.VideoExtraction`), not one game: `extract_video` reads player names once, from the first detected game, rather than once per game, since one video is one match and the same two players hold for every game in it -- re-reading per game would just be redundant OCR cost. `extract_video` only ever writes JSON — it never touches DuckDB. `json_export.write_video` writes one pretty-printed JSON file per video, grouped one directory per season (`<json_dir>/season-<season>/<video_id>.json`, `matches/` by default, see `json_export.video_path`) rather than flat across every season a tournament has run, with video-level fields (video_id, match_date, season, match_type, player_red_name, player_blue_name, commentators, metadata, num_games, red_score, blue_score, winner) alongside a `games` list holding every game the video contains (game_index, timestamps, game_type, winner, win_line, square_texts, events — a game has no name of its own, see `models.GameResult`; a file written before the "GAME N" label was dropped also carries a `label` key per game, which `read_video` simply ignores — no need to strip it by hand) — this exists so a contributor can hand-review/correct one video's extraction results (all its games at once) in a plain text editor. `video_url` is prompted for interactively alongside match_date/season/match_type (`cli._prompt_video_url`, empty allowed — a contributor extracting from a video someone else downloaded may not have the link handy) and `extracted_at` is the extraction date (`date.today()`), not a DB-write timestamp. A non-blank `video_url` is checked against `cli._is_youtube_url` (hostname in `{youtube.com, www.youtube.com, m.youtube.com, youtu.be}`) — light on purpose, no network call to confirm the video actually exists, just enough to catch a pasted-wrong-link mistake. `--video-url` is validated *before* `extract` starts the (multi-minute) extraction pipeline, not inside `_prompt_match_metadata` (which runs on a background thread overlapping extraction) — otherwise a bad flag value wouldn't surface as an error until everything else had already finished. A match is unique by player names + match date, which `video_id` already encodes (see `_video_id` above) — so re-running `extract` on the same match (not necessarily the same video file: a re-download of the same match hits this too) collides on the same `<json_dir>/season-<season>/<video_id>.json` path. `--if-exists` left unset (the default) asks interactively whether to replace it, via `extract_video`'s `on_duplicate: Callable[[Path], bool] | None` callback — the same deferred-resolution pattern as `on_missing_game_type` (see below), for the same reason: `video_id` isn't known until deep into the pipeline (it needs the first game's OCR'd player names), so the check can't happen upfront in the CLI before extraction starts. The CLI's `on_duplicate` wraps `typer.confirm`, guarded by the same `progress_lock` as `on_missing_game_type` so it can't interleave with the progress bar or the metadata prompts. Declining leaves the existing JSON file untouched and `extract_video` returns an `ExtractionSummary` with `skipped=True` (`num_games`/`num_claims` meaningless at 0) rather than raising — it's a normal user choice, not a failure. `--if-exists replace`/`--if-exists error` bypass the prompt entirely (an explicit answer given upfront), falling through to `json_export.write_video`'s existing unconditional-overwrite/raise behavior. A caller of `extract_video` that passes neither an explicit `if_exists` nor an `on_duplicate` callback (there's no one to ask) gets a `ValueError` on a genuine duplicate, rather than silently overwriting — the old implicit `if_exists="replace"` default was judged too easy to accidentally clobber a prior extraction with, now that duplicates are meant to be caught rather than iterated over.
- Each event in a game's `events` list also carries a `square_text` key, e.g. `"square_text": "Kill 3 enemies"` a couple of lines from that same event's `"row": 1, "col": 1` — a contributor hand-reviewing the JSON directly (the common case this file format exists for) would otherwise have to cross-reference every claim's row/col against the game's `square_texts` grid by hand to know what was actually claimed. It's write-only, not a `models.GameEvent` field: `json_export._event_to_dict` looks it up from the enclosing game's `square_texts` at serialize time (`_event_square_text`, returning `None` for a game-level event with no row/col, or for a square outside a hand-edited/ragged grid) the same way `display._square_text` already does for `match show --events`, and `read_video` doesn't read the key back — storing it on `GameEvent` itself would let it drift from `square_texts` if a contributor corrected an OCR misread there without also updating every event that touched that square.

- The five fields that describe the *video file* rather than the match it records — `video_url`, `duration_s`, `published_at`, `source_path`, `extracted_at` — are grouped under their own `"metadata"` key in the JSON (`json_export._metadata_to_dict`, issue #47), rather than sitting at the top level alongside `video_id`/`match_date`/`player_red_name`/etc: a contributor skimming a file for the match-identifying fields would otherwise have to pick them out from among provenance/technical detail that isn't about the match itself. `models.VideoExtraction` keeps these as its own flat dataclass fields regardless — the grouping is a JSON presentation choice, not a model change, so every other module (`extract.py`, `db.py`, `display.py`) reads `extraction.duration_s` etc. exactly as before. `read_video` therefore can't just index `data["metadata"][...]`: a file written before #47 has these fields at the top level with no `"metadata"` key at all, so it resolves `metadata = data.get("metadata", data)` first — falling back to the whole document for the old flat layout — and reads every field off that, unchanged from before otherwise.
- `VideoExtraction.duration_s` is the **whole video's** length in raw seconds (`frames.probe`), not the sum of its games': a broadcast also contains intros, between-game "POST GAME" recaps and post-match talk, so it can't be recovered from the game segments after the fact — `extract_video` probes for it upfront. It's stored raw (like `start_video_ts_s`/`end_video_ts_s`, unlike an event's human-readable `game_timer`) and only formatted as `HH:MM:SS` for display, by `display.format_duration` in `match show`. The field is optional/defaulted to `None` throughout — dataclass, JSON, and the nullable `videos.duration_s` DB column — for two reasons: a video whose fps can't be read has no duration to record (`frames.probe` returns `0.0` there, which `extract_video` converts to `None` rather than writing a fabricated zero), and JSON files written before the field existed must still read back. That last case is why `json_export.read_video` reads this key off `metadata` (see above) with `.get`: a `KeyError` would make `match list` report an otherwise-valid extraction as an unparseable old-format file. `db.write_extraction` prefers `extraction.duration_s` (the JSON is the source of truth, hand corrections included) and only falls back to `video_info.duration_s` when the JSON has none. `db.py`'s schema also carries an `ALTER TABLE videos ADD COLUMN IF NOT EXISTS duration_s DOUBLE` after the `CREATE TABLE IF NOT EXISTS` block, since the latter leaves an already-created `videos` table alone and every insert into a pre-existing database file would otherwise fail on an unknown column. `games.win_line` is added the same way, for the same reason — note a column added by `ALTER` carries no `CHECK` constraint, unlike one declared in the `CREATE TABLE`; the values come from `models.WinLine` either way, so the constraint is a backstop rather than the thing keeping them valid (`test_schema_accepts_every_win_line_value` is what catches the SQL list drifting from the enum).
- `VideoExtraction.published_at` is when the video was uploaded to YouTube (yt-dlp's `upload_date`), distinct from `match_date` (when the match was actually played, user-supplied) and `extracted_at` (when this extraction ran) — three different dates that can legitimately disagree (a match played one day, uploaded the next, extracted weeks later). It's read off the same yt-dlp invocation that downloads the video, not a separate lookup: `download_video`'s single `--print-to-file` call already asks yt-dlp for `after_move:filepath`, so it costs nothing extra to have that one template also print `%(upload_date)s` on the same line (tab-separated — a filesystem path and an 8-digit date can't contain one, so splitting on it is unambiguous without a second temp file). `video.download.DownloadResult` carries both `path` and `published_at` back to the caller as a result of this. That means it's only ever known when *this run* did the downloading: `extract`'s URL branch in `cli/app.py` passes the downloaded result's `published_at` straight through to `extract_video`'s own `published_at` parameter, while a locally-supplied video (or a URL typed in at the `--video-url` prompt for a video someone else already downloaded) was never fetched by this run and so has no metadata to read it from — `extract_video` leaves the field as whatever was passed (`None` by default) rather than making its own separate network call to look it up after the fact, which would cost an extra yt-dlp invocation just for one supplementary field. Optional/defaulted to `None` throughout for the same two reasons as `duration_s` — no download this run means nothing to record, and a JSON file written before this field existed must still read back — including the same `data.get` treatment in `json_export.read_video` and the same `ALTER TABLE videos ADD COLUMN IF NOT EXISTS published_at DATE` in `db.py`.
- The match's outcome is summarized by three more derived properties alongside `num_games`, all four working the same way: `red_score`/`blue_score` (how many games each player won) and `winner` (`models.MatchWinner`: `red`/`blue`/`draw`). `MatchWinner` is its own enum rather than a reuse of `CellColor` because `draw` is a real *match* outcome that no single game has — a playoffs match is two games and is allowed to end 1-1. `winner` is `None` ("undetermined") in two cases rather than guessing: a match with no games, and a match where any game has no winner recorded — in the latter the scores don't account for every game, so naming the current leader (or calling an even split a draw) would invent a result from incomplete data. That's exactly what `validation`'s `match_outcome_undetermined` rule already reports, and `_check_match_outcome`'s draw rule is now written in terms of `extraction.winner is MatchWinner.DRAW` rather than its own `Counter`. `display.format_outcome` renders the value as prose for `match list`'s `RESULT` column and `match show`'s header, naming the winning *player* rather than just their color (`WinLine.label` is the same idea one level down). It's the only thing that reads the score directly, and only for the `None` case: an undetermined match is shown as a standing ("alice leads 1-0, 1 undecided") rather than a win, so the CLI can't end up calling a match for someone the property itself declined to.
- How many games a match consists of is exposed as `VideoExtraction.num_games`, but it is a **property** (`len(self.games)`), not a stored dataclass field — the games list is the only place that count lives, so the two can't drift apart the way a persisted copy could when a contributor hand-edits a JSON file to add or drop a game. It's still *written* in both persisted forms — a `num_games` key sitting directly above the JSON's `games` list (with `red_score`/`blue_score`/`winner` next to it, same deal), and a denormalized non-null `videos.num_games` DB column (so "how many games did this match go?" is answerable off `videos` alone, no join and `GROUP BY` against `games`; `videos.red_score`/`blue_score`/`winner` join it, the last nullable since an undetermined outcome has nothing to name) — but none of them is ever *read* back: `json_export.read_video` ignores those keys entirely, exactly like a pre-`GAME N`-removal file's per-game `label`, and re-derives the count from the games actually present. That also means a JSON file predating the field needs no special handling on read (unlike `duration_s`/`win_line`, which are genuinely unrecoverable when absent), and that `load-db` backfills `videos.num_games` correctly from such a file. `db.py` carries the usual `ALTER TABLE videos ADD COLUMN IF NOT EXISTS num_games INTEGER` for pre-existing database files — nullable there, since an `ALTER` can't invent a value for rows already written, unlike the `NOT NULL` in the `CREATE TABLE`. `display.render_match_table`/`display.render_match` and `validation._check_game_count` all read the property rather than calling `len()` themselves, so the count they print/check is the same one that's persisted.
- Reflecting that JSON into DuckDB is a separate, optional step: the `load-db` CLI command (`db.load_json_dir`) reads every `*.json` file under a directory, including its season subdirectories (as written by `write_video`, see `json_export.video_path`), and calls `db.write_extraction` once per file — no cross-file grouping needed, since one file already is one video. `json_export.read_video` is the inverse of `write_video`. Since `write_extraction` can now be called from JSON alone with no source video file in hand, `source_path` and `video_info` (resolution/fps) are optional and stored as DB `NULL` in that case — `videos.source_path` is nullable in the schema for the same reason (match_date/season/match_type/player names/extracted_at aren't nullable, since `VideoExtraction` always has them). This split (extract → JSON always; JSON → DB only on request) means the JSON file, not the database, is the source of truth: a contributor's manual correction to a JSON file is what `load-db` re-reflects, and the database is disposable/regeneratable from it at any time. The three pre-existing files under `matches/` predate this one-file-per-video structure (they're one-file-per-game) and won't load — re-run `extract` on those videos to regenerate them in the current format.
- `extract`'s `video_path_or_url` argument accepts either a local file (as before) or a youtube.com/youtu.be URL, so a match can be downloaded and extracted in one command instead of two — this is why it's typed `str`, not `Path`, at the CLI level: `Path("https://...")` silently collapses the double slash after the scheme (`Path("https://x").`→`"https:/x"`), so converting it before checking whether it's a URL would corrupt it. `cli._is_youtube_url` (the same check used for `--video-url`) decides which case applies. When it's a URL: it's downloaded via `download_video` into `--download-dir` first, extraction runs against the downloaded file, and that file is deleted afterward *only* if extraction succeeded — this cleanup logic explicitly tracks whether *this run* downloaded the file (`downloaded_path`), so a locally-supplied video is never touched regardless of outcome. If extraction raises, the user is asked (`typer.confirm`) whether to keep the downloaded video before the original exception is re-raised unchanged (a bare `raise`, not wrapped) — so a failure still surfaces with its real traceback, just with one extra prompt first. `--keep-video` skips deletion outright on both paths (including the failure-path confirm prompt, not just the success-path delete) for a contributor who wants the footage kept around regardless of outcome — e.g. to re-run extraction locally after a calibration fix rather than re-downloading. As a bonus consequence of accepting a URL here, if `--video-url` (the provenance field stored in the JSON) wasn't separately given and `video_path_or_url` itself was a YouTube URL, that URL is reused for it too — no reason to make a contributor paste the same link twice.
- The overlay itself literally prints the answer for each game's type: a small "BASE GAME"/"DLC" subtitle directly under the "GAME N" label. `game_type_label.py` OCRs that box (`layout.GAME_TYPE_BOX`) and is `extract_video`'s first choice for `GameResult.game_type` — it's read off the same frames already grabbed for square-text majority voting (`_SQUARE_TEXT_FRAME_COUNT`, no extra decode cost), majority-voted the same way for the same reason (a single frame's OCR can misread, or land on a transition moment where the subtitle isn't rendered at all). `game_type_label.parse_game_type_label` only accepts an exact "BASE GAME"/"DLC" match, returning `None` for anything else, including a misread — guessing wrong here would silently mislabel a game, so a `None` just means "no vote", not "guess". This small a subtitle is sensitive to source bitrate: it reads reliably off full-quality downloaded match footage, but not off this repo's intentionally recompressed test fixtures (`hud_start.png`/`hud_partial.png`/`clip_claim.mp4`) — which is why those fixtures still exercise the `squares.py`/`on_missing_game_type` fallback path in tests, never the direct read.
- Each game is either a **base game** or **DLC** (Shadow of the Erdtree) game, per its goal squares — `squares.py` is now only `extract_video`'s fallback for `game_type`, used when the direct overlay read above comes back `None` for every sampled frame. It infers this from `squares.json` (alongside it), a hand-maintained, growing reference mapping every square text seen so far to the game type it belongs to. There's no programmatic way to know this, so the reference only knows what's been added to it; it **ships empty**, meaning every game fails to infer until someone populates it. `squares.infer_game_type` returns `None` (not a guess) when none of a board's 25 squares are in the reference; if the matched squares disagree (which shouldn't happen — a board's squares come from one pool, not a mix), the majority wins and a warning is logged rather than failing outright. `extract_video` calls this per game *during* the main per-game loop (cheap, no I/O), but only resolves a `None` result — via the `on_missing_game_type: Callable[[GameResult], GameType] | None` callback, or a `ValueError` if none was given — in a second pass *after* `match_metadata` is awaited, not inline: both can ultimately require interactive prompting (`cli._prompt_game_type`, `--game-type` to skip it — one flag answers it for every game in the video that needs it, not per game, since a whole match being one type is the common case), and resolving game type first would mean two prompt sequences racing each other on the terminal at once. `GameResult.game_type` defaults to `None` in the dataclass (not enforced non-`None` by the type system) since a hand-edited JSON file can legitimately clear it back to unknown — `db.py`'s `games.game_type` column is nullable for the same reason, unlike the video-level fields in `write_extraction` that `VideoExtraction` always guarantees.
- The CLI shows a progress bar (`typer.progressbar`) for `extract`, since a full video can take minutes to process at ~1 sample/second. `extract._collect_observations` accepts an `on_progress` callback fired once per sampled frame (including frames later skipped as non-gameplay, since decode cost is paid either way), and `extract.estimate_sample_count` gives the CLI an upfront total (`ceil(duration_s * sample_rate_hz)`, an estimate — exact count depends on where decoding stops near the end) to size the bar before extraction starts.
- `frames.sample_frames` decodes sequentially with `cap.grab()`/`cap.retrieve()` rather than seeking to each target timestamp with `CAP_PROP_POS_MSEC` — profiling showed the seek-per-sample pattern cost ~2.5x more than sequential grab+skip on a real clip, since `CAP_PROP_POS_MSEC` forces a jump back to the nearest preceding keyframe and a forward decode to the target on *every single sample*. This was a genuinely free win (same yielded timestamps/frames, no behavior change) — but it's a minority of extraction's total runtime: profiling the full pipeline on the committed fixture showed OCR (`pytesseract`, which shells out per call) at ~80-90% of wall time, with the per-sample `timer.read_timer` OCR call alone responsible for roughly half of it. It is now the *only* per-sample OCR call: the game-label read that used to run alongside it (throttled to every 5th sample) is gone with the label itself.
- OCR calls that don't depend on each other run concurrently via a `ThreadPoolExecutor`, since each `pytesseract` call blocks on an external `tesseract` subprocess and releases the GIL while waiting — this took the fixture clip's end-to-end extraction time from ~11.4s to ~2.8s (measured with `cProfile`/wall-clock timing, not just an estimate). Two call sites: `extract._collect_observations` submits each sample's timer OCR to a shared pool bounded by `_OCR_WORKERS` (`min(8, os.cpu_count())`), gated by a `threading.Semaphore` acquired before every `submit()` — without that bound, decoding (now fast, see above) would race far ahead of OCR and queue the entire video's frames in memory before any of them finished processing; results are still collected in original sample order afterward, so downstream ordering (segmentation, event diffing) is unaffected. `board.cell_square_texts` parallelizes its 25 independent per-cell reads the same way, but as one unbounded one-shot batch (`max_workers=len(crops)`) since it only runs once per detected game, not once per video sample. Neither call site changes *what* gets OCR'd or how often — only wall-clock time — so there's no accuracy tradeoff here, unlike throttling the timer read would be.
- Square (goal) text is read from `_SQUARE_TEXT_FRAME_COUNT` (10) frames spread evenly across a game's segment, not a single frame — a single frame's OCR occasionally misreads a cell (motion blur, a transient compression artifact), and unlike cell color/claims there's no debounce available here since square text is static for the whole game, so `extract._select_square_text_observations` picks up to 10 evenly-spaced observations from the segment, `extract._grab_frames` decodes each (sharing one `VideoCapture` rather than reopening the file per frame), and `board.cell_square_texts_majority` OCRs all 25 cells on every one of those frames and keeps, per cell, whichever exact text string was read most often. This only runs once per detected game, so the ~10x OCR cost over the old single-frame read is a one-time-per-game expense, not a per-sample one.
- `tests/fixtures/clip_claim.mp4` is a short (13s), re-encoded, full-resolution clip trimmed from a real match, covering exactly one known claim transition — downscaling it for size once broke goal-text OCR (crops became too small to read reliably), so it's kept at source resolution instead and just trimmed/re-encoded to stay small.
- Every committed fixture (`hud_start.png`, `hud_partial.png`, `hud_commentators.png`, `clip_claim.mp4`, `clip_base_game.mp4`, `clip_dlc_game.mp4`, `clip_game_boundary.mp4`) has the webcam/face regions blacked out (players' and commentators' likenesses aren't needed for testing the overlay-reading logic) — done by zeroing everything outside the grid column and score-bar strip except the timer, game-type and commentator-nameplate boxes, which sit inside those columns and are still needed (a nameplate is printed text, not a likeness, so keeping it doesn't reintroduce what the redaction is for). (Fixtures committed before the "GAME N" label was dropped as a signal still show it — they were generated while `GAME_LABEL_BOX` was in the restored set, and there's no reason to regenerate them over it. Likewise, `hud_start.png`/`hud_partial.png` predate the commentator boxes being added to the restored set and so read back as no commentators found — see `commentators.py` — rather than being regenerated just for this.) `hud_commentators.png` is a dedicated fixture for `commentators.py`'s real-OCR path, the same reason `clip_base_game.mp4`/`clip_dlc_game.mp4` exist for `game_type_label.py`. `scripts/redact_fixture.py` is the tool that does this (and trims, for a clip); it derives the kept regions from `layout.py`'s boxes rather than hand-measured pixels, so recalibrating the template keeps fixture generation correct for free. Always run new footage through it rather than committing raw frames.
- `clip_base_game.mp4` and `clip_dlc_game.mp4` are 5s (16-frame) clips trimmed from the base-game and DLC halves of one real match, and exist specifically to cover `game_type_label.py`'s real OCR path — the older fixtures can't, since their recompression destroys the subtitle (see above). They're deliberately encoded at a much higher quality (`redact_fixture.py` uses CRF 16) for that reason; a redacted frame is overwhelmingly black, so this still costs only ~390KB each. Both are also short enough to run the *whole* `extract_video` pipeline on, which is what `test_extract_video_reads_game_type_from_the_overlay_subtitle` does — end-to-end, with no `squares.json` entries and no prompt callback. Note `test_extract_video_raises_without_a_way_to_resolve_game_type` depends on the *opposite* property of `clip_claim.mp4` (its subtitle not OCR'ing), so re-encoding that fixture at higher quality would break it.
- `clip_game_boundary.mp4` is a 28s clip trimmed around a real *game boundary* — the tail of game 1 (claimed board, stopped clock), the splash between the two games, then game 2's empty board and pre-game countdown — cut from the same 3fps source as the two above, so it's the same ~450KB. It's the only fixture with more than one game in it, and exists to cover segmentation end-to-end (`test_extract_video_splits_a_clip_spanning_two_games`): every earlier fixture is single-game, which is why a bug that collapsed every video into one game could ship green. Both of segmentation's board-reset and timer-reset signals fire inside it; 28s is about the shortest window that holds enough of both games for that.
- Every Typer group in `cli/app.py` (the top-level `app` and the `match_app` sub-app) is constructed with `no_args_is_help=True`, so a bare `scadustats` or `scadustats match` prints that group's full command list instead of Typer's default `Missing command` error, which names none of the commands it's complaining about. The exit code stays Click's usage-error 2 — no command was given, that just gets a useful answer now, unlike an explicit `--help`, which is a successful 0.
- `match list`, `match show` and `match validate` (`cli/app.py`) are sub-commands of a `match_app` Typer sub-app (`app.add_typer(match_app, name="match")`), grouped together since all are read-only lookups over already-extracted matches, as opposed to `extract`/`load-db` which produce/mutate them. All read JSON files directly via `json_export.read_video`, not the database — consistent with the JSON being this project's source of truth (see above), they work whether or not `load-db` has ever been run, and all three take the directory the same way, as `--json-dir` (`match list` used to take it as a positional argument instead, which meant the one command you'd reach for first was also the one spelled differently from its siblings). `cli._read_matches` is the shared walk of that directory for the two commands that take no `video_id`: it globs `<json_dir>/**/*.json` (every season subdirectory — see `json_export.video_path`) and skips a file that fails to parse as a current-format extraction — e.g. one of the pre-existing one-file-per-game files that predate the one-file-per-video format — with a warning on stderr (`KeyError`/`ValueError`, which also covers `json.JSONDecodeError`, a `ValueError` subclass) rather than aborting the whole run. Sorting is by filename alone, not the full path or an explicit sort-by-date: a filename is `<video_id>.json` and `video_id` starts with the match date (see `extract._video_id`), so filename order already is chronological order for free — sorting by the full path instead would sort first by season subdirectory name, and a season is free text rather than a sortable number (`"10"` sorts before `"6"`, and a season needn't even be numbered at all), so that would put a later season's matches ahead of an earlier one's. `cli._match_path` is the other shared piece — `match show`/`match validate` both turn a `video_id` into a path by searching every season subdirectory for `<video_id>.json` (a video_id doesn't say which season it's filed under on its own), and a missing file is a `typer.BadParameter` (a mistyped id is a user mistake, not a traceback).
- Everything those commands print is rendered by `display.py`, which cli/app.py only echoes: every function there takes models and returns lines, printing nothing, so the formatting is testable without a `CliRunner` (`tests/cli/test_display.py`) and cli/app.py stays about flags and prompts. Nothing in it interprets an extraction — a game's result is shown exactly as the JSON records it, never recomputed from its events, since `match validate` is where the two are cross-checked and a silently "corrected" display would hide the very disagreement that command exists to surface. `match list` renders a padded table (`render_table`, shared with the `--events` listing) of `MATCH / SEASON / TYPE / GAMES / RESULT`: the match date and both player names are deliberately *not* their own columns, since `video_id` already spells out `<date>-<red>-vs-<blue>` and repeating them is what crowded out the one thing the old ragged one-line-per-match listing didn't say at all — how each match ended. That result (`format_outcome`) says "leads" rather than "wins" while any game has no winner recorded, so a score that only looks final isn't presented as one: an undecided game is usually an extraction problem. `match show` prints, per game, the recorded result in prose plus the **final board** — replayed from the game's own events by `winner.replay`, with the winning line's cells bracketed (`render_board` renders every cell three characters wide, bracketed or not, so the grid stays square and a completed line is visible as a shape). Showing the replayed board next to the recorded result is deliberate: that's exactly the pair `validation._check_recorded_winner_matches_board` compares, so a mismatch is visible where it happened. `--events` (off by default — 25+ rows per game buries the summary) adds a per-game table of every event with its video timestamp, game clock, player, square and goal text, ordered by `video_ts_s` for the same reason `validation._ordered_events` is: the clock counts *down* through the pre-game countdown, so ordering by it would file `GAME_START` in among the claims. Goal texts are truncated to keep rows scannable (the JSON has the full text), and a `square_texts` grid too short to index — OCR output, hand-editable — yields `""` rather than taking down a read-only listing.
- `winner.replay`/`winner.apply_event`/`winner.empty_board` are the one event-replay implementation, shared by `extract._determine_winner` (final board only), `validation._board_states` (every intermediate state, for locating when a win settled) and `display.render_game` (final board, to draw it). They live in `winner.py` rather than `board.py` because they're pure board logic with no frame/OCR/cv2 involvement, next to the win conditions evaluated over the same board. `apply_event` is a no-op for an event carrying no `row`/`col` (`GAME_START`), so replaying a game means walking its whole event list rather than a filtered copy of it.
- `validation.py` checks an extracted match against the tournament's own rules, surfaced as `match validate` (one `video_id`, or every file in `json_dir` when omitted — same skip-with-a-warning tolerance as `match list`, and a non-zero exit when anything was found, so a batch of extractions can be gated on it). It's a **review aid, not a gate on extraction**: nothing in the pipeline calls it, and a failing rule doesn't mean the video was bad — it means the JSON says something the rules say can't happen, so an OCR misread or a missed game boundary probably slipped through and a contributor should look at that file. Checks are therefore written to point at *what* looks wrong, never to guess a correction. `validate_extraction` returns a flat `list[ValidationIssue]` (`code`, `message`, `game_index`) rather than raising or returning a bool, since one file can violate several rules at once and all of them are worth printing; `code` is a stable greppable rule id, `game_index` is `None` for a match-level rule *including* one whose message names a game (an undetermined match outcome is a defect of the match, not of the game that lacked a winner). Match-level rules (game count per match type, base-then-DLC for the first two games, a determinable outcome, a double-elimination decider present exactly when the first two games split) run before the per-game ones, in game order. Two deliberate non-cascades: an undecided game suppresses the decider/draw rules (with the score unknown they'd be guesses piled on top of the one real problem), and "no marks after the win" is skipped when the recorded winner already disagrees with the board. That last rule also only applies to a **line** win, and locates the win by walking the replayed board states *backwards* from the end: a line ends the game the moment it completes, but a line can also be completed and immediately undone (see `extract._extract_events`), so only the win that persists to the end counts. A **majority** win is exempt entirely — it's decided by who leads when time runs out, and every line is typically blocked long before that, so players legitimately keep claiming squares afterward; checking it there would flag every majority game in the corpus. Replay order is by `video_ts_s`, not `game_elapsed_s`, since the latter counts *down* during the pre-game countdown and would misplace `GAME_START` among the claims. `win_line` is checked as part of `winner_board_mismatch` rather than as a rule of its own (a win recorded on a line the board doesn't hold is the same defect as one recorded for the wrong color), with one exception: a result that agrees with the board in every respect *except* that `win_line` is absent gets its own `win_line_not_recorded` code, since that's a JSON file predating the field rather than the board contradicting the result — every match extracted before it reports this until re-extracted. `match_validate` itself (unlike `match list`/`match show`) builds its own output directly in `cli/app.py` rather than through `display.py`, since it's a diagnostic report rather than a presentation of the JSON — each match's line is colored green "ok" or red "N issues", and each issue below it names its scope in cyan and its rule `code` dimmed, via `typer.style`/`typer.colors`. No `--no-color` flag is needed for a script piping the output: `typer.echo` (via click) already strips the ANSI codes whenever the destination isn't a terminal, which is also why `tests/cli/test_app.py`'s validate tests can assert on the plain text through `CliRunner` — only `test_validate_output_is_colorized_when_color_is_supported` forces `color=True` to check the codes are actually emitted.

## Testing

- Test runner: `pytest` (dev dependency, declared under `[dependency-groups] dev` in `pyproject.toml`).
- Tests that hit real external services (currently: downloading an actual YouTube video) are marked `@pytest.mark.integration`.
- `[tool.pytest.ini_options] addopts = "-m 'not integration'"` excludes integration tests by default, so a plain `uv run pytest` (or local dev loop) stays fast and offline.
- Run integration tests explicitly with `uv run pytest -m integration`.

## CI

- GitHub Actions workflow at `.github/workflows/ci.yml`, triggered on push to `main` and on pull requests.
- Steps: install `ffmpeg` and `tesseract`, install `uv` (`astral-sh/setup-uv`), `uv sync --locked`, `uv build`, `uv run pytest` (unit tests, default marker filter applies), then `uv run pytest -m integration --deselect tests/video/test_download.py::test_download_video`.
- Only `tests/video/test_download.py::test_download_video` is excluded from CI: it hits real YouTube via `yt-dlp` to download a video, and GitHub Actions runner IPs get throttled/bot-detected by YouTube badly enough to cause CI timeouts. Every other test marked `integration` (currently just `test_square_text_majority_vote_reads_all_cells_from_real_clip`, which only decodes a committed fixture clip — no network involved) runs in CI as its own step, deselecting just that one test. Run `test_download_video` locally instead (see Testing section).
